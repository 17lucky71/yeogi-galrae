# 05. 성능·확장 및 운영 계획

지금 서비스는 과제용 규모(동료 몇 명이 테스트하는 수준)에 맞춰 만들었습니다.
이 문서는 **① 지금 적용한 응답 지연 개선**, **② 사용자가 늘어났을 때의 확장 계획**, **③ 비용·키 운영 정책**, **④ 프레임워크로 전환할 때의 영향**을 정리합니다.

---

## 1. 응답 지연 개선

AI 코스 추천은 요청 1번에 보통 10~20초가 걸립니다. 대부분 AI가 긴 JSON을 만드는 시간이라서, **"AI를 덜 부르고, 부를 때는 짧고 빠르게"** 가 원칙입니다.

### 1-1. 이미 적용한 것

| 방법 | 구현 위치 | 효과 |
|---|---|---|
| **결과 캐시** | `api/recommend.py` → `cache_key()`, `cache_get()`, `cache_set()` | 같은 조건(지역·기간·동행·스타일·추가 요청)으로 1시간 안에 다시 요청하면 AI를 부르지 않고 **즉시 응답**. 공백·대소문자·스타일 선택 순서가 달라도 같은 요청으로 인식. 최대 100개까지 저장하고 오래된 것부터 삭제 |
| **지연 체감 줄이기** | `js/main.js` | 로딩 표시, 8초가 넘으면 "조금 오래 걸려요" 안내, 30초가 넘으면 자동 취소 + 다시 시도 버튼 |
| **모델당 타임아웃** | `GEMINI_TIMEOUT_SECONDS = 20` | 한 모델이 멈춰도 무한정 기다리지 않음 |
| **모델 자동 전환** | `GEMINI_MODELS` | 할당량 초과(429) 시 다음 모델로 바로 넘어가서 실패 대신 응답 |
| **입력 길이 제한** | 지역 30자, 추가 요청 200자 | 프롬프트가 짧아져 처리 시간과 비용 감소 |
| **소요 시간 로그** | `print(f"[{request_id}] 200 cached=… 12.3s")` | Vercel 로그에서 요청별 응답 시간과 캐시 적중 여부를 확인해 개선 효과 측정 |

> 참고: 이 캐시는 서버리스 함수가 켜져 있는(warm) 동안만 유지되는 **가벼운 메모리 캐시**입니다. 함수가 꺼지면 사라지지만, 추가 비용이나 외부 서비스 없이 바로 적용할 수 있어 첫 단계로 선택했습니다.

### 1-2. 설정만 바꾸면 되는 옵션 — 경량 모델 우선

`GEMINI_MODELS` 환경 변수 순서만 바꾸면 **작고 빠른 모델을 먼저** 쓰도록 전환할 수 있습니다. 코드 수정이나 재작성 없이 Vercel 환경 변수 변경 + Redeploy로 끝납니다.

```
# 기본값 (품질 우선)
GEMINI_MODELS=gemini-3.8-flash,gemini-3.7-flash,gemini-3.5-flash-lite,gemini-3.1-flash-lite

# 속도 우선 (경량 모델 먼저)
GEMINI_MODELS=gemini-3.1-flash-lite,gemini-3.5-flash-lite,gemini-3.8-flash
```

선택 기준: 동료 테스트처럼 품질이 중요할 때는 기본값을 쓰고, 사용자가 몰려 응답 시간이 길어지면 속도 우선으로 바꿉니다. 바꾼 뒤에는 로그의 소요 시간을 비교해서 효과를 확인합니다.

### 1-3. 다음 단계로 설계해둔 개선안

| 개선안 | 방법 | 예상 효과 | 고려할 점 |
|---|---|---|---|
| **공유 캐시** | 메모리 캐시 대신 Redis 같은 외부 저장소 사용 (예: Vercel Marketplace의 Upstash Redis) | 함수가 꺼져도, 여러 인스턴스 사이에서도 캐시 공유 → 적중률 상승 | 외부 저장소 설정·비용 |
| **인기 조합 미리 생성** | "강릉 1박 2일 친구" 같은 인기 조합을 하루 한 번 미리 만들어 저장 (Vercel Cron) | 인기 요청은 항상 즉시 응답 | 무료 할당량을 미리 소모 |
| **출력 길이 제한** | 하루 일정 수를 4~5개로 제한하고 설명을 1문장으로 요청 | 생성할 글자가 줄어 응답 시간 단축 | 결과가 덜 풍부해질 수 있음 |
| **스트리밍 응답** | AI가 만드는 대로 조금씩 화면에 표시 | 첫 글자가 1~2초 안에 보여 체감 대기 시간 감소 | JSON을 완성 전에 그려야 해서 화면 코드가 복잡해짐 |
| **2단계 생성(요약 우선)** | 먼저 코스 제목·장소 목록만 빠르게 받고, 설명은 뒤이어 채움 | 핵심 정보를 먼저 보여줌 | AI 호출이 2번으로 늘어남 |

## 2. 확장 계획 (사용자가 늘어났을 때)

| 단계 | 상황 | 대응 |
|---|---|---|
| 현재 | 동료 테스트 수준 (하루 수십 건) | 서버리스 함수 + 메모리 캐시 + 모델 자동 전환 |
| 1단계 | 하루 수백 건, 무료 할당량 부족 | 유료 요금제 전환, 공유 캐시(Redis) 도입, 경량 모델 우선 |
| 2단계 | 동시 요청이 몰려 대기·실패 증가 | **요청 제한(rate limit)**: IP당 분당 N회로 제한해 한 사람이 할당량을 독점하지 못하게 함 |
| 3단계 | 요청이 아주 많아 20초씩 붙잡고 있기 어려움 | **비동기 처리 + 작업 큐**: 요청을 받으면 작업 ID만 바로 돌려주고, 백그라운드 작업자가 큐에서 하나씩 AI를 호출. 화면은 몇 초마다 결과를 확인(polling)하거나 완료 알림을 받음 |

### 비동기 처리 구조 (3단계 설계안)

```
[브라우저] --POST /api/recommend--> [함수] --작업 등록--> [큐]
     ↑        (작업 ID 즉시 반환)                           ↓
     └--GET /api/result?id=...  <--결과 저장-- [작업자] --AI 호출
```

장점: 사용자가 많아도 서버리스 함수가 오래 붙잡혀 있지 않고, 실패한 작업은 큐에서 자동으로 재시도할 수 있음
단점: 구조가 복잡해지고 큐·저장소 같은 외부 서비스가 필요함

### 서버리스라서 좋은 점 / 한계

- 좋은 점: 요청이 늘면 Vercel이 함수를 자동으로 여러 개 띄워 줌(별도의 로드밸런서 설정 불필요), 요청이 없으면 비용이 거의 없음
- 한계: 함수 실행 시간 제한(`vercel.json`의 `maxDuration: 60`초), 처음 켜질 때 느린 **콜드 스타트**, 함수끼리 메모리를 공유하지 않음(→ 공유 캐시 필요)

## 3. 비용·키 운영 정책

### 3-1. 비용 관리

- **무료 할당량 모니터링**: Google AI Studio의 사용량 화면(https://aistudio.google.com)에서 하루 사용량 확인
- **유료 전환 시**: Google Cloud 결제 계정에 **예산 알림**(예: 월 1만 원의 50%·90% 도달 시 메일)을 설정
- **불필요한 호출 줄이기**: 결과 캐시, 입력 길이 제한, 요청 중 버튼 비활성화(연타 방지)
- **남용 방지**: 2단계 확장 시 IP별 요청 제한 도입

### 3-2. API 키 교체(롤오버) 절차

정기 교체(예: 90일마다)와 유출 의심 시 즉시 교체를 같은 절차로 진행합니다. **새 키를 먼저 넣고 → 동작을 확인한 다음 → 옛 키를 삭제**해서 서비스가 끊기지 않게 합니다.

1. Google AI Studio에서 **새 키 발급** (옛 키는 아직 유지)
2. Vercel → Settings → Environment Variables → `GEMINI_API_KEY` 값을 새 키로 교체 → **Redeploy**
3. 배포 URL에서 AI 추천을 한 번 실행해 정상 동작 확인
4. AI Studio에서 **옛 키 삭제**
5. 교체 날짜를 기록 (다음 교체일 계산)

유출이 의심될 때는 1번보다 **옛 키 삭제를 먼저** 해서 피해를 막고, 잠깐의 서비스 중단을 감수합니다.

### 3-3. 자동화 계획

- 정기 교체 알림: 캘린더 반복 일정(90일)으로 시작
- 규모가 커지면: Google Cloud Secret Manager에 키를 저장하고 교체 주기를 설정, 배포 시 자동으로 최신 키를 주입
- 유출 감지: GitHub의 **Secret scanning**(공개 저장소에 키 패턴이 올라오면 알림)을 켜 두고, 알림을 받으면 위의 즉시 교체 절차 실행

### 3-4. 권한 관리

- Vercel 프로젝트와 Google AI Studio 계정은 본인만 접근 (팀 작업 시 Vercel의 Project Members에서 역할을 최소 권한으로 부여)
- 키는 Production/Preview 환경에만 넣고, 로컬 테스트용 `.env`는 GitHub에 올리지 않음 (`.gitignore`)

## 4. 프론트/백엔드 분리 구조의 장단점과 프레임워크 전환 영향

### 4-1. 지금 구조(바닐라 HTML/CSS/JS + `api/` 서버리스 함수)

| 장점 | 단점 |
|---|---|
| 키가 서버에만 있어 **보안**이 단순함 | 화면이 커지면 JS로 직접 DOM을 다루는 코드가 길어짐 |
| 빌드 과정이 없어 **배포가 빠르고 설정이 적음** | 공통 부품(헤더, 카드)을 여러 페이지에서 재사용하기 불편 |
| 프론트와 백엔드를 **따로 고쳐도 서로 영향이 적음** (API 명세만 지키면 됨) | 프론트(JS)와 백엔드(Python) 언어가 달라 입력 검증 규칙을 두 번 작성 |
| `git push`만 하면 Vercel이 둘 다 자동 재배포(CI/CD) | 테스트 자동화를 직접 구성해야 함 |

### 4-2. 프레임워크(예: Next.js, React)로 전환한다면

| 영역 | 영향 |
|---|---|
| 화면 코드 | `index.html` + `main.js`를 컴포넌트 단위로 다시 작성해야 함. 상태 관리(로딩/오류/결과)는 더 깔끔해짐 |
| 백엔드 | Next.js는 API도 JavaScript로 작성하므로 `recommend.py`를 JS로 옮기거나, Python 함수를 그대로 두고 호출만 유지할 수 있음 |
| API 명세 | 02번 문서의 요청·응답 형식을 그대로 유지하면 화면만 바꿔도 백엔드는 수정할 필요가 없음 → **명세를 먼저 정해둔 덕분에 전환 비용이 줄어듦** |
| 배포 | Vercel이 Next.js를 기본 지원하므로 Framework Preset만 바꾸면 됨. 대신 빌드 단계가 생겨 배포 시간이 조금 늘어남 |
| 보안 | 키 관리 방식(서버 환경 변수)은 동일. 단, 프레임워크에서 `NEXT_PUBLIC_`처럼 브라우저로 노출되는 변수에 키를 넣지 않도록 주의 |
| 과제 조건 | 이번 미션은 프레임워크 사용 금지라 전환하지 않음 |

## 5. 운영 지표 (개선 효과를 확인하는 방법)

| 지표 | 확인 방법 | 목표 |
|---|---|---|
| 평균 응답 시간 | Vercel 로그의 `[요청ID] 200 … 12.3s` | 20초 이하 |
| 캐시 적중률 | 로그의 `cached=True` 비율 | 반복 요청이 많을수록 상승 |
| 실패율 | 로그의 429/502/504 건수 | 하루 요청의 5% 이하 |
| 할당량 사용량 | Google AI Studio 사용량 화면 | 일일 한도의 80% 이하 |
